# ZUK-3256 implementation receipt

## Authorized behavior

Run the first real Zukan consumer pilot through the signed private marketplace
release. The public bootstrap must migrate the existing alpha.4 installation
without silently claiming legacy state, altering repository policy or harness
configuration, discarding historical evidence, or bypassing reviewable PR
publication.

## Red evidence

The inherited updater rejected Zukan's symlinked legacy release lock and had no
explicit migration route. New focused tests first failed because the CLI did
not recognize `--migrate-legacy`, legacy inventory verification did not exist,
and no transaction could replace or restore the old managed links.

Threat-model iterations added coverage for nested legacy skill digest ordering,
drifted legacy evidence, explicit opt-in and release selection, failure after
the old workflow directory is backed up, failure after new links are installed,
and publication of the bounded legacy `current` link removal.

## Material choices

- Migration is accepted only by `update --release <exact> --migrate-legacy` and
  only when the recognized symlinked legacy lock layout is present.
- The new release is authorized and cryptographically verified before legacy
  mutation. The old lock, allowed vendor inventory, byte-bounded regular files,
  skill tree digests, workflow digests, and every managed link are then proved.
- Repository `AGENTS.md`, harness configuration, unrelated skill entries, and
  the old immutable vendor tree remain untouched. Only installer-owned pin,
  workflow, binary, and skill-link paths are declared to `--pr`.
- The workflow-directory replacement has an explicit backup state, and every
  mutation phase rolls back links, lock, current pointer, evidence, and new
  materialization on failure.

## Independent review

The standards review found two legacy-validation gaps before the fixed point:
the updater read the symlinked legacy lock before proving the intermediate
`current` target, and a regular file directly under `skills/` was allowed by the
vendor prefix check without belonging to a digest-locked skill. The correction
now inspects link metadata before reading, constrains `current` to one validated
release below the vendor root, inventories only regular byte-bounded files, and
requires every skill payload file to belong to a lock-listed skill. Regression
tests prove both an escaping `current` link and an unlocked skill file fail
before mutation.

The transactional review expanded injected failures across all state changes:
after workflow backup, after link replacement, after release-lock replacement,
and after legacy-current removal. Every case restores the old lock, current,
workflow and skill links and removes the new bin, vendor, and evidence paths.

The intent review found the implementation remains within ZUK-3256: migration
is explicit, the consumer policy and harness settings remain unchanged, the old
vendor evidence is retained, all three declared harnesses receive the same
canonical skills, and publication remains an opt-in bounded PR operation. No
remaining actionable finding was identified. PR/CI evidence will be appended
before publication.
